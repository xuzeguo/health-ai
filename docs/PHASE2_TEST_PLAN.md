## 1. 先测试设计，后开发，再以证据放行

本文件先于二期实验和业务实现编写。用户审查通过后，每个阶段仍须在编码前把本阶段案例落实到任务清单，冻结输入、预期值、观察点、命令、超时及隔离方案；不得边写实现边降低预期。P0 的输入依赖供应商时，先固定协议与失败条件，实测后记录能力差异并决定降级，不修改失败记录冒充通过。

每个案例至少包含：ID、关联需求、前置条件、输入/动作、精确预期、测试层级、所需资源、执行命令、结果/证据位置。下表已给出场景与判定条件；具体自动化文件名和命令随阶段开工前细化，不预先宣称尚不存在的脚本可运行。

开发顺序：测试规格 → 可自动化案例/fixtures → 证明关键失败场景能够失败 → 业务实现 → 相关测试 → 全阶段回归 → 记录结果。首次因目标尚不存在而失败可以作为开发过程记录，阶段退出时不得留下失败用例。对真实模型非确定性结果，用固定数据集和明确分母判定，不将某次回答文本完全一致作为标准。

放行规则：本阶段必测全部通过，累计离线全回归 `pnpm test` 和 `pnpm build` 通过，新增运行时能力及受影响浏览器/网络场景验证通过，缺陷关闭且证据齐全，才能进入下阶段。P0 无生产实现，但实验判定表、已有项目离线回归和能力选择记录也必须完成。

任何必测项失败、超时或因环境未执行，都记为失败/未验证并阻止阶段退出；不得当作跳过即成功。无关原生能力被明确放弃时，须在能力矩阵保留失败结果并证明批准的替代路径满足同一需求。涉及范围或标准变化先给用户审查。

## 2. 公共前置条件和证据

- 使用临时SQLite、合成Key、合成或授权脱敏报告、受控本地端口；不访问日常真实库，不打印/覆盖 `.env`。
- 固定clock、UUID/排序输入和受控延迟，验证并发用同步屏障而非盲目sleep；计时断言留合理平台余量，并有硬超时。
- Mock负责确定性故障和边界；实际供应商/Embedding/LangChain能力另做真实抽样，Mock不替代这些验收。
- 版本记录包含源码revision或内容hash、Node/pnpm、依赖lock、模型/Prompt/Schema/索引/数据集版本。
- 每项保存pass/fail、计数、错误分类、耗时和命令退出码；报告不得保存Key、报告全文、完整对话、私有reasoning。
- 测试目录/进程/连接/定时器结束后清理；重复执行结果不依赖上一轮残留。
- 每阶段同时测试成功、非法输入、边界、超时/取消、状态一致性和资源释放，实际适用项见下表。
- 脱敏扫描同时检查stdout/stderr、JSON报告、浏览器可见事件及生产bundle，使用可识别合成敏感标记作为断言。
